# 参照仓库：墨鸽 Inkdove 的做法清单

参照仓库为 `https://github.com/Bowen1314/inkdove`，克隆在 `reference/inkdove`（已加入 `.gitignore`，不入库）。
本文件只记录**做法**（流程、约束、测试与文档习惯），不涉及其业务，也不抄其代码。每个阶段开工前重读一遍。

阅读顺序与时间：2026-10-29，按 README.md → SPEC.md → SPEC-phase2.md「测试要求」→ DESIGN.md 第 0–2 节 → docs/deviations.md 前 20 条 → docs/external-apis.md 前 30 行 → docs/development.md → server/test/ 三个测试文件 → `git log` 前 60 条。

## 一、契约与规格

1. **把「唯一契约」这件事写进规格正文。** SPEC 开头明确写：后端和前端两人并行开发，本文件是唯一契约，「路由、字段名、枚举值必须一字不差」。出处：`SPEC.md` 第 8 行。抄法：我的 SPEC 开头同样声明这是唯一契约，并声明代码、测试、文档以它为准。

2. **歧义的处理方式预先规定，而不是临时决定。** 同一处写「有歧义按"最简单、能跑通"处理，并在「偏离规格」一节写明」。出处：`SPEC.md` 第 8 行、`docs/deviations.md` 开头。抄法：SPEC 第 0 节就写死这条规则，deviations 从第 1 条开始编号。

3. **规格里每个接口都写失败情形，不只是成功响应。** 例如蒸馏接口一次列了三种失败：已在跑返回 409 `job_running`、没资料返回 400 `nothing_to_distill`、模型没配返回 400 `llm_not_configured`。出处：`SPEC.md` 第 124 行。抄法：我的每个命令/路由下方必须有「失败」小节，逐条给退出码或 HTTP 状态码 + 机器码。

4. **规格没定的错误码，事后集中补一条 deviations。** 第 6 条一次性列出 400/401/403/404/409/429/502 各状态码下新增的机器码，并说明「agent 访问别人的号时先判权限再判存在，不存在的号也返回 403，探不出别人的号是否存在」。出处：`docs/deviations.md` 第 6 条。抄法：开发中冒出的每个新机器码都补进 deviations，不散落在代码里。

5. **把「不做」写成明确的非目标清单。** SPEC 开头两句直接限定单租户、一个管理员密码登录，避免被要求做多租户。出处：`SPEC.md` 第 3–6 行。抄法：SPEC 首屏给「第一版只做这一个核心流程」+「非目标」两条清单。

6. **测试要求按功能逐条列成可勾选的清单，含失败路径。** phase2 的「测试要求（后端）」按 F8/F11/F12/F10/F7/F1/F2/F3/F4/F5/F6 分组，每组列出必须覆盖的用例，例如「token 只能用一次，过期失效」「不能动最后一个 admin」「连续失败 3 次自动暂停」「进程重启后 running 的任务接着发」。出处：`SPEC-phase2.md` 第 744–789 行。抄法：我的 SPEC「测试要求」一节按功能编号列出用例，每个失败路径一条，写清断言什么。

## 二、配置、密钥与错误

7. **所有环境变量统一项目前缀，并显式禁止读通用名变量。** 表头写「只能读带 `INKDOVE_` 前缀的；**禁止读取** `LLM_API_KEY`、`OPENAI_API_KEY`、`LLM_BASE_URL` 等通用名」。出处：`SPEC.md` 第 33 行。抄法：配置模块只接受本项目前缀，读不到就直接用默认值，绝不回落到 `OPENAI_API_KEY`。

8. **密钥只写不回显，接口只给「是否已设置」和末四位。** 设置结构里是 `apiKeySet:false, apiKeyLast4:null`，写入走专用字段，传空串表示清空、不传表示不变；并写明「任何接口都不回传明文，日志里不打印」。出处：`SPEC.md` 第 51、72、100 行。抄法：同一套语义（set / last4 / 传空清空 / 不传不变）。

9. **错误响应统一成 `{error, code}`，error 是给人看的中文。** 出处：`SPEC.md` 第 56 行。抄法：完全照此，另外要求 error 里不带密钥、带对方返回的状态码。

10. **对外部服务的错误信息要「带状态码 + 带对方 message + 抹掉密钥」，并用测试断言。** 测试里用真实的 key 串构造 401 响应体，断言 `!err.message.includes(KEY)`，同时断言 4xx 不重试、429/5xx/529 重试 2 次。出处：`server/test/llm.test.js` 第 140–173 行。抄法：同样的断言方式，作为安全回归测试保留。

## 三、Mock 与测试辅助

11. **Mock 由环境变量切换，且行为规则写成确定的数字。** `INKDOVE_LLM_MOCK=1` 时「extract 每块产出 2–3 条；含"人工"或"human"时 category=handoff；含"写代码""code""翻译""ignore previous"时 category=offtopic」等等，全部写死在规格里。出处：`SPEC.md` 第 345 行。抄法：我的 mock 规则同样逐条写进 SPEC，测试直接断言这些数字（例如条目数 2–3）。

12. **测试实例一次一份临时数据目录，测试结束删掉。** `startApp()` 里 `fs.mkdtempSync(path.join(os.tmpdir(), 'inkdove-test-'))`，`close()` 里 `fs.rmSync(dataDir, ...)`，并且默认 `INKDOVE_LLM_MOCK=1`、外部地址指向连不上的端口（`http://127.0.0.1:9`）。出处：`server/test/helpers.js` 第 28–43、152–157 行。抄法：同结构，测试永不碰真实数据目录、永不联网。

13. **所有等待时间都可注入，测试里给 0。** `humanize: ZERO_HUMANIZE`、`mockDelayMs: 0`、`wahaPollMs: 20`、`notifyRetryDelayMs: 10` 等作为 `createApp` 的选项传入；`INKDOVE_UPDATE_CHECK=0` 关掉外部检查。出处：`server/test/helpers.js` 第 13、45–72 行。抄法：把时钟、退避、轮询间隔都做成可注入参数，测试里设为 0 或毫秒级。

14. **等条件成立，不等固定时长。** `waitFor(fn, { timeout = 4000, interval = 20 })` 轮询直到返回真值，超时抛错并带业务说明（「会话 xxx 的消息迟迟没有 botDecision」）。出处：`server/test/helpers.js` 第 162–171 行。抄法：全项目禁止裸 `sleep` 等结果，统一用 waitFor 式轮询，超时信息写清在等什么。

15. **假外部服务的 payload 形状按真实抓包/源码核对，并在注释里写依据。** helpers 里假 WAHA 的注释写「以下两点按 GOWS 2026.9.2 实测：start 一个已经在运行的 session 什么也不做…logout 后 session 自己重启」，还有「实测：顶层 name 是 null，名字在 _chat.name」。出处：`server/test/helpers.js` 第 262–268、423–424 行。抄法：我的假服务同样在注释里注明字段依据（文档链接或实测日期），避免假服务比真服务宽松。

16. **假服务要能摆出「坏情况」，不只是 happy path。** 假 WAHA 有 `failSend`、`failChats`、`failChatList`、`failChatMessages`、`sendDelayMs`、`codeError`、`contentLength`（只发头不发体）、`chunked`、`maskSecrets` 等开关。出处：`server/test/helpers.js` 第 270–326 行。抄法：假服务按「超时 / 5xx / 429 / 返回格式不对 / 慢响应 / 截断」逐项留开关。

17. **有一个可替换的 AI 钩子层，能统计调用次数和最后一次参数。** `aiHooks()` 对 `generate/review/draft/suggest/...` 每个方法包一层，可用 `hooks.generate = fn` 覆盖，`hooks.calls.generate` 计数，`hooks.args.generate` 记参数。出处：`server/test/helpers.js` 第 566–585 行。抄法：我做同样的 `hooks` 层，这样能断言「失败时不发送」「只调了一次审核」这类行为。

## 四、外部接口核实

18. **每个外部接口先核实再写代码，记录文档链接、实测日期、版本和结果。** external-apis.md 里有「2026-10-12 实测，GOWS 2026.9.2」这样的标注，也有「按文档写的，还没在真机上核实」的显式声明。出处：`docs/external-apis.md` 第 23–35 行。抄法：我的 external-apis.md 每条给 URL + 核实日期 + 结论；没核实的不写进代码。

19. **对「文档没写、只能实测」的细节单独列出来，并标明哪部分需要真机验证。** 例如「GOWS 入站消息是否填 replyTo 文档和源码都没找到证据…**这两点要用真机验证**」。出处：`docs/deviations.md` 第 14 条。抄法：我的 deviations 里也留一节「需要真实环境验证的点」。

## 五、文档与提交

20. **README 的结构固定：logo → 一句话卖点 → 只放真实徽章 → 风险须知 → 适用于/不适用于 → 功能（每条链接到 features.md）→ 截图 → 快速开始（前置条件/步骤/最少必填配置表/首次设置）→ 对外访问 → 升级 → 常用命令 → 文档索引 → 许可证。** 「使用前须知」如实写风险，功能条目结尾统一 `[详细](docs/features.md#锚点)`。出处：`README.md` 第 28–67、94–209 行。抄法：照这个骨架写，但内容全部换成我的项目；README 只做索引，细节放 docs/features.md。

21. **README 的每个数字都要能复现。** 「三个容器的内存上限合计约 1.4GB」「20 万条消息 30 天约 0.3 秒」这类都写了测量条件。出处：`README.md` 第 100 行、`git log` 中的看板提交说明。抄法：我 README 里的性能数字必须写清数据规模和机器条件，测不出来就不写。

22. **功能说明单独成篇且带锚点。** README 每条功能结尾 `[详细](docs/features.md#推荐回复和话术)`，features.md 写完整行为和实现约定。出处：`README.md` 第 51–65 行。抄法：同样的 README→features.md 两层结构。

23. **DESIGN.md 先写「要去掉的东西」。** 第 0 节用 9 条列出第一期界面的结构性毛病（窄卡片叠在灰底上、标题前的彩色图标方块、页面顶部提示条、标题下的解释句、每个字段都有说明、空顶栏、向导式页面、大号引导卡片、卡片里的表格），每条写「改成什么」。出处：`DESIGN.md` 第 5–17 行。抄法：我的 DESIGN 第 0 节列 ≥10 条 AI 界面通病，每条给替代做法。

24. **设计 token 与「页面 css 不准写死颜色字号」写成硬规则。** token 表给浅色/深色两套、每个色值可查；规则写「页面文件只能用 components.css 和 layout.css 里的类…页面 css 里禁止重新定义颜色、字号、圆角、阴影，要用就引用变量。不写行内 style」。出处：`DESIGN.md` 第 21–35、38–95 行。抄法：同样的 token 结构 + 同样的禁令，并在审查阶段逐条对照。

25. **重活拆成「一个功能一个提交」，提交说明写用户可见的行为变化和关键数字。** 例：「看板加「平均回复时间」和按业务员筛选：客户发来消息到有人回复…平均等多久，旁边是中位数和次数；客户连着发几条算一轮，从第一条算起；…一条 SQL 用窗口函数算，不加索引，20 万条消息 30 天约 0.3 秒」。出处：`git log --format='%s'`。抄法：提交说明一律「做了什么 + 具体规则 + 关键数字」，不写「fix bug」。

26. **发版流程写进 development.md：tag → CI 校验 tag 与版本号一致 → 跑测试 → 构建 → 建 Release。** 「推了 `vX.Y.Z` 标签后，GitHub Actions 会：1. 检查标签和两个 package.json 的 version 一致，跑后端测试；2. 构建镜像…；3. 建 GitHub Release」。出处：`docs/development.md` 第 47–53 行。抄法：CI 里先断言 tag == package.json version，再跑测试，最后建 Release；我只做本地提交与本地 tag，不配置远端发布。

27. **健康检查接口暴露运行模式，便于排错。** `GET /api/health` 返回 `{ok, version, mock, llmConfigured, channel, waState}`，并且允许不登录访问（deviations 第 16 条解释了这样做的取舍）。出处：`SPEC.md` 第 66 行、`docs/deviations.md` 第 16 条。抄法：我的 doctor/health 输出同样字段，并说明哪些信息会泄露、如何避免。

28. **测试用「形状断言」锁接口，防止字段漂移。** 例如 `assert.deepEqual(Object.keys(s).sort(), ['chars','createdAt',...])`、`assert.deepEqual(Object.keys(job).sort(), [...])`。出处：`server/test/sources.test.js` 第 91 行、`server/test/distill.test.js` 第 79–82 行。抄法：为每个对外实体写一条 key 集合断言，字段增删都会让测试失败并逼着更新 SPEC。

29. **安全类行为写进规格并配可执行的测试，而不是靠自觉。** 「金丝雀串是每次进程启动时随机生成的一个短串，用来发现提示词泄露」，测试里注入 `canary: 'INKDOVE-cafebabe1234'` 并断言 system prompt 含它、客户消息里的分隔标记被转义成全角。出处：`SPEC.md` 第 266 行、`server/test/llm.test.js` 第 205–224 行。抄法：凡是有「模型可能泄露/编造」的地方，都埋金丝雀串或原文核对，并用测试固定。

30. **把「测试怎么摆弄时间」写成规格义务。** 「每日上限和发送窗口，测试里注入时钟」「发送间隔，注入成 0」。出处：`SPEC-phase2.md` 第 762–764 行。抄法：规格里凡是时间相关的规则，都注明测试如何注入。

## 六、结构上照搬、业务换掉的部分

31. **单进程 + SQLite + 单目录数据**：SQLite 一个文件、上传/数据放 `./data`，备份 = 打包目录。出处：`SPEC.md` 第 38 行、`README.md` 第 189 行。抄法：本地工具更应该这样，数据一个目录，备份一条 `tar`。

32. **`docs/` 分层：features / development / deviations / external-apis（+ deploy）**，README 只做索引。出处：`README.md` 第 199–209 行。抄法：完全同构。

33. **发布前自查清单落到文档而不是记忆**：`docs/development.md` 里写「改了 Dockerfile…先手动跑一次构建检查」。出处：`docs/development.md` 第 45 行。抄法：我的 development.md 写「发版前手动跑一遍全量测试 + 从零安装」的具体命令。
